Three names, three jobs

Git ≠ GitHub ≠ VS Code

VS Code

Where you edit files and can use a graphical Git experience.

Git

Distributed version control. Commits, branches, history — on your machine.

GitHub

Hosts Git repositories and adds pull requests, reviews, rules, Actions and collaboration.

You can use Git without GitHub. You can use Git without VS Code.

Repository

Your project plus its history.

Local

Files you edit + the Git database in .git.

files+history=repo

remote means a saved connection from your local repository to another repository URL.

Local ↔ remote

Four commands move history across the gap.

fetch only updates your view of the remote. pull also integrates, so it can change files or surface a conflict.

01
Mental model

Branches

Not copies of folders. Movable names pointing into the same history.

Start here

main is just a branch pointer.

Commits do not move. Branch pointers do.

You are here

HEAD is Git's “you are here” marker.

Read it as a chain

  • HEAD points at a branch name
  • the branch points at a commit
  • the commit is a full snapshot

Switch branches and HEAD follows. The commits never move.

Point HEAD straight at a commit instead of a branch and Git calls it a detached HEAD: “you are not on a branch right now.”

Create a branch

One command. One new pointer. No copy.

$ git switch -c feature/security-score
Switched to a new branch
'feature/security-score'
Commit on the branch

The commit is new. Only this branch moves.

$ git add .
$ git commit -m "Add security score"
[feature/security-score e31a] ...
Parallel work

Meanwhile, main moves too.

GitHub enters the story

A pull request says: “Can we integrate this?”

Not a Git command

  • Compare head branch → base branch
  • Discuss the diff
  • Run checks
  • Request reviews
  • Merge when ready
Integrate

Merge brings the work back together.

GitHub supports merge commit, squash merge and rebase merge. We only need the concept today.

Two shapes of merge

Why you sometimes get a merge commit — and sometimes don't.

Fast-forward

main never moved while you worked. Nothing to reconcile — Git slides the pointer forward. No new commit.

Three-way

Both sides moved. Git finds the common ancestor, combines both, and writes a merge commit with two parents.

For the labs, use squash merge: GitHub turns the branch into one tidy commit on main.

When histories collide

A merge conflict is Git asking for human intent.

<<<<<<< HEAD
retry_count = 3
=======
retry_count = 5
>>>>>>> feature/security-score

Git can see both edits.

It cannot know whether the correct result is 3, 5, or something else.

Conflict = ambiguity, not corruption.

Repository boundaries

Forks

A branch is another pointer in one repository. A fork is another repository.

Branch or fork?

Same history concept. Different boundary.

Fork topology

One local repo can know multiple remotes.

↕sync / PR
pierre/security-hub
remote name: origin

remote is the concept. origin and upstream are conventional names, each mapped to a repository URL.

Rule of thumb

When do we want a fork?

Are we collaborating inside the same repository?
BRANCH

Usually the simplest team workflow when you have write access and shared governance.

FORK

Useful for open source, no upstream write access, experimentation, or a deliberate repo boundary.

Public repository hygiene

Never use Git history as a secret store.

{
  "tenant": "demo.onmicrosoft.com",
  "clientSecret": "super-secret-123"
}

.gitignore is not secret protection.

  • Do not commit credentials in the first place
  • Deleting in the next commit does not remove old history
  • Use secret scanning
  • Use push protection where available
local change→push protection→GitHub→secret scanning

Vocabulary check

Eleven words worth leaving with.

  • clone — bring a repository and its history locally
  • branch — movable pointer to a commit
  • stage — select content for the next commit
  • commit — record a snapshot in history
  • push — send commits to a remote
  • remote — saved name for another repository URL
  • fetch — download remote history
  • pull — fetch then integrate
  • merge — integrate histories
  • fork — separate repository linked to an upstream
  • PR — proposal to integrate one branch into another
